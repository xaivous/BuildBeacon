## Part 1. The story in one paragraph

A Jötunn mod stub that would not compile became a finished Valheim 1.0 building piece over two days: a beacon that
takes boss trophies and makes their materials free to build with nearby. Almost all of the work was not writing
gameplay code. It was making the loop between an AI assistant, an IDE, a game engine and a running game fast and
honest: a build that actually deploys, a log that says what went wrong, console commands that answer questions the
assistant cannot see, and a Unity connection that lets the assistant rebuild art assets itself. By the end, that
loop is captured as three reusable skills and a small tool, and the assistant can take a texture change from Unity
into the running game without a human touching anything but the game.

## Part 3. The dev loop

The loop the video should explain. Everything else in this document is an instance of it.

```
                 ┌──────────────────────────────────────────────────────────────┐
                 │                       Claude Code                            │
                 │  reads: git, source, csproj, BepInEx log, Unity console,     │
                 │         console-command dumps, game assembly metadata        │
                 │  writes: C#, csproj, .mat YAML, skills, docs                 │
                 └───────┬───────────────────────┬──────────────────────────────┘
                         │ edit                  │ Unity MCP (RunCommand / Import / GetConsoleLogs)
                         ▼                       ▼
      ┌─────────────────────────┐    ┌──────────────────────────────┐
      │ Rider / .csproj / .sln  │    │ Unity 6000.0.75f1            │
      │ (user works here too)   │    │ BuildBeaconUnity project     │
      └───────────┬─────────────┘    │ materials, prefab, FBX, icon │
                  │ dotnet build     └──────────────┬───────────────┘
                  ▼                                 │ BuildPipeline.BuildAssetBundles
      ┌─────────────────────────┐                   ▼
      │ MSBuild                 │    ┌──────────────────────────────┐
      │  Jötunn prebuild        │◄───│ Assets/Output/buildbeacon    │  copy into BuildBeacon/Assets/
      │  compile + embed bundle │    └──────────────────────────────┘  (embedded as a resource)
      │  publish.ps1 → r2modman │
      └───────────┬─────────────┘
                  │ BuildBeacon.dll into Dev profile plugins
                  ▼
      ┌─────────────────────────┐
      │ Valheim (user launches) │───► BepInEx/LogOutput.log ───────────┐
      │  F5 console:            │───► beacon_dump / _materials / _prefabs ─┤ back to Claude
      │  screenshots by user    │──────────────────────────────────────────┘
      └─────────────────────────┘
```

Three variants of the loop, as they settled by the end:

- **Code loop** (skill `build-deploy`): edit C# → `build-and-verify.sh` → confirm the deployed DLL timestamp moved,
  Valheim is not holding the file, the bundle is still embedded → user launches → `log-tail.sh` → next edit.
  Typical cycle time once the setup was right: 2 to 5 minutes, dominated by the game launch.
- **Unity loop** (skill `unity-bundle`): edit `.mat`/prefab in Unity or on disk → `Unity_ManageAsset Import` →
  `Unity_RunCommand` builds the bundle → `copy-bundle-and-build.sh` → same as the code loop from there.
  By the end the assistant ran this whole chain itself; the user's only job was to look and describe.
- **Diagnose loop** (skill `valheim-debug`): symptom → read the log first → if the log is silent, ask the game
  through a console command → if the question is about game code, check the assembly with `sigdump` (signatures,
  callers, or `--il` disassembly) → fix.
- **Blender loop** (added on the 22nd, documented in `unity-bundle`): patch the generator script in Blender's Text
  editor through the Blender MCP → run it to regenerate the mesh → viewport screenshot to confirm → export the FBX
  straight over the Unity asset → the Unity loop from there. The assistant drives all of it; the user judges the
  screenshots and the game.

The rule that made the loop honest: every step verifies its own output. MSBuild says "Build succeeded" even when
the deploy copy failed because the game had the file open, so the script checks the timestamp. The csproj can
lose its embedded-resource entry without any error, so the script checks the DLL's manifest. Harmony reports a bad
patch as a warning and silently drops every other patch with it, so the log tail highlights it.

## Part 4. Timeline

### Chapter 1. "Cannot find UnityEngine.MonoBehaviour" (Sep 21, 14:14 to 14:53)

**Goal.** Get the Jötunn stub compiling in Rider.

**What happened.** The session started in a scratch folder; Claude moved itself into the project. The stub's
csproj never imported `Environment.props`, so `VALHEIM_INSTALL` fell through to Jötunn's registry lookup, which
returned a dead install on `F:\SteamLibrary` (only BepInEx and a doorstop remained there). Every game DLL
reference resolved against a folder with no `Valheim_Data`, hence 74 "could not locate assembly" warnings and the
MonoBehaviour error. First fix used `$(SolutionDir)`, which is undefined when building the csproj directly, so it
did nothing; the working fix imports the props by `$(MSBuildThisFileDirectory)` and adds a `SolutionDir`
fallback. The first build then ran the Jötunn prebuild, which generated the publicized assemblies.

**Artifacts.** `BuildBeacon/BuildBeacon.csproj` (imports at the top), `BuildBeacon/Environment.props`.

**Decision.** Fix the build so it works from both the `.sln` (Rider) and the bare `.csproj` (command line), so the
assistant and the IDE never disagree about what builds.

**Video beat.** The registry-path reveal via `dotnet msbuild -getProperty:VALHEIM_INSTALL` is a good "the tool
can see what you can't" moment.

### Chapter 3. Making the piece its own thing (15:2x to 15:33)

**Goal.** Stop the beacon behaving like a ward.

**What happened.** Jötunn's `CustomPiece` clones the whole `guard_stone` prefab, `PrivateArea` included, so the
piece had ward RPCs, ward hover text and triggered Hugin's ward tutorial. Removing that one component with
`DestroyImmediate` (a deferred `Destroy` is too late; Jötunn registers the prefab immediately after) kept the mesh,
ring projector and glow and dropped all the behaviour. Added English localization, Valheim 1.0 build-menu usage
tags (`PieceConfig.Usage`, needing Jötunn 2.30), and a proper description. Checked the game's `Piece` class fields
by reflection to learn about the new usage-tag bitfield rather than guessing.

### Chapter 4. The panel, and the first real bug (15:33 to 15:51) — commit `90f2076`

**Goal.** A trophy panel (list view) with unlimited slots, then: "the deductions show in the panel but not in game".

**What happened.** Panel built on Jötunn's `GUIManager`. Then the BepInEx log showed the cause of the missing
discount: HarmonyX refused to patch `Player.PlacePiece` because in 1.0 it is `void` and the reference postfix asked
for `__result`. One failed patch aborts `PatchAll`, so *no* patches were active. Traced the 1.0 call flow with a
metadata scan of the assembly: `UpdatePlacement → HaveRequirements → TryPlacePiece → ConsumeResources`, which
means the old approach of wrapping `HaveRequirements` alone would have left a gap at the consume step even without
the crash. Wrapped `UpdatePlacement` with a depth-counted resource swap.

**Artifacts.** `BuildBeacon/Patches/RequirementPatches.cs`, `BuildBeacon/BeaconUI.cs`, `tools/sigdump` (born here
as a throwaway in a temp folder), `media/01-panel-first-render.png` (15:59; header text hanging off the panel's
left edge, icon half a row low: Jötunn's `CreateText` leaves a centre pivot).

**Decision.** Never trust a patch signature from memory or older mod code; read it from the assembly.

**Video beat.** Log line → "every patch is missing, not just this one" → the assembly trace. This is the strongest
"why the tooling matters" moment on day one.

### Chapter 5. Refunds, layout, rules file (15:53 to 16:17) — commits `21b291a`, `5ee0370`, `427ab22`

**Video beat.** "It works by accident" → show why it would break → show the fix. Good brainstorming/design beat.

### Chapter 7. Unity will not open the project (00:39 to 00:47, and 12:19 to 12:2x) — commits `37066ce`, `a25dcf2`, `c6a43dd`

**Goal.** Open `BuildBeaconUnity` in Unity 6000.0.75f1 to build the beacon model.

**What happened.** Three waves of errors, each a plugin-import setting:

1. `media/02-unity-displayname-errors.webp` (00:39). Eleven `CS0592: Attribute 'DisplayName' is not valid on this
   declaration type` in the Timeline and Input System packages. `assembly_utils.dll` defines a field-only
   `DisplayNameAttribute` in the global namespace; plugin DLLs are auto-referenced by every assembly; C# resolves
   enclosing namespaces before `using` directives. Fix: Auto Reference off.
2. `media/03-unity-version-error.png` (00:43). `Cannot create an instance of the abstract type 'Version'`:
   `assembly_valheim.dll` has a static global class `Version` shadowing `System.Version`. Same fix, applied to
   every game DLL.
3. `media/04-unity-yamldotnet-errors.webp` (12:19). `Unable to resolve reference 'YamlDotNet'`: Jotunn.dll
   references it, nothing ships it, Mono loads lazily so the game never notices, Unity validates eagerly.
   Fix: Validate References off. The user's guess (a DLL leaking from their play profile) was reasonable and wrong;
   the assistant proved it by finding no such file anywhere in the Dev profile.

All three are recorded in the repository README's "Unity project notes" for future-you.

**Artifacts.** The `.meta` files under `BuildBeaconUnity/Assets/Assemblies/`, `README.md` section.

**Video beat.** The C# name-lookup explanation with the two shadowed types. Short, surprising, reusable.

### Chapter 13. Geometry into the game, and a silent collapse (23:00 to 23:16) — commits `3883f29`, `d3d966d`, `b64b105`

**Goal.** Get the abacus into the build without losing the tuned materials, then brighten the dark stone.

**What happened.** Before exporting, the source of truth for materials was settled: the FBX importer's material
remap binds each Blender material name to the project's `.mat` asset, so Unity keeps the look across re-exports.
Unity owns colour and emission; Blender owns geometry and slot names. The script's palette was rewritten to mirror
Unity's values as a preview only. Then the full Blender loop ran end to end from the assistant: regenerate, export
over the Unity FBX, save, reimport, verify the five material slots still pointed at the `.mat` files, rebuild the
bundle, copy, build, deploy. The dark stone tint went from 0.13 to 0.45 so the black marble texture reads.

Then the beacon started shattering seconds after placement again, with nothing in the log, exactly like day two.
The prefab hadn't changed and neither had the code. Three log-only Harmony patches on `WearNTear.ApplyDamage`,
`Destroy` and `Remove` were added for beacons; the next run showed one wear tick applying 1,000 damage, the full
health, with no hit data. A new `--il` mode in `tools/sigdump` disassembled `UpdateWear` and the branch read: *if*
`m_noSupportWear` *then check support, and deal 100% if there is none*. The flag means the opposite of its name.
The prefab had it on with material Stone, so the beacon demanded stone-grade support and a wooden deck killed it.
The ward has it off; so does the beacon now, along with `m_supports`.

**Decision.** When the log is silent, make the game speak: diagnostics that only fire for our objects are cheap
to leave in permanently.

**Artifacts.** `BuildBeacon/Patches/DiagnosticPatches.cs`, `tools/sigdump` (`--il`), the `valheim-debug` skill's
note on the inverted flag.

**Video beat.** The strongest debugging sequence in the project: silent failure → stack trace → disassembly → one
boolean. Show the three lines of IL.

## Part 6. Design evolution of the mod

1. **Reference design** (other thread): trophies give flat/percent discounts; upgrade items add levels; slot cap.
2. **First playable** (Sep 21): unlimited slots, list-view panel, refund modes, readable rules file.
3. **Rework** (Sep 22 00:11): two pools. Boss trophies free their biome's materials and grow the beacon; mob
   trophies give small discounts floored at a minimum; no upgrade items; one of each boss trophy per beacon.
4. **Data pass** (00:34): every build ingredient mapped to a boss by biome, forty creature rules, all generated from
   a CSV and validated against the game's item database at startup.
5. **Look** (Sep 22 afternoon): own model; vanilla black marble and grausten on the stone; crystal-wall glass with a
   blue glow on the crystal and runes; ring and glow borrowed from the ward and centred on the crystal.
6. **Finish** (Sep 22 evening): the crown gains an abacus between capital and cap; the dark stone tint is lifted so
   the marble reads; the beacon stops pretending to be structural; stone build, hit and demolish effects; the glow
   becomes the wisp torch's blue light on the crystal.

Decisions worth narrating: folding the Core plugin into the mod (one DLL, one Thunderstore package); forcing one boss
trophy per beacon; making the server's rules files the source of truth and syncing through Jötunn's admin-only
config rather than a custom RPC; keeping colour in Unity and structure in code.
